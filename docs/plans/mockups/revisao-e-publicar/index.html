Revisão e Publicar — a etapa mágica

Hoje, "Publicar" abre um PR e a tarefa some — o momento mais importante (a mudança da pessoa indo para o app) acontece invisível, no GitHub. A proposta: dividir em Revisão (o time olha) e Publicar (entra no app), com a pessoa acompanhando a revisão de dentro do Inhouse, corrigindo apontamentos com o Claude, e uma celebração de verdade quando o merge acontece.

1 O nome da etapa

OpçãoComo fica a esteiraPrós / contras
Revisão RECOMENDADO… Seu teste → Revisão → PublicarCurto como os outros pinos; faz par com "Seu teste" (o seu → o do time). Tooltip completa: "o time de engenharia revisa antes de publicar".
Time… Seu teste → Time → PublicarMais curto ainda, porém vago — "time" de quê?
Aprovação técnica… Seu teste → Aprovação técnica → PublicarPreciso, mas longo e burocrático.

Nos textos (não no pino), sempre por extenso: "revisão da engenharia". Apps locais sem GitHub pulam a etapa — vai direto de "Seu teste" para "Publicar", como hoje.

2 A esteira nova

Onde essa tarefa está: Revisão Espec Plano Aprovação Execução Verificações Seu teste Revisão Publicar ⏳ com a engenharia

"Revisão" é um pino redondo (não é uma porteira SUA — é a vez do time). O chip à direita mostra com quem está a bola: "⏳ com a engenharia" ou "✋ com você" (quando pedem ajustes).

3 Enviar para revisão (o card que substitui o "Publicar abre um PR")

Pronto para a revisão

Verificações e o seu teste aprovados. Agora o trabalho vai para o time de engenharia revisar — nada muda no app até eles aprovarem.

Você acompanha tudo por aqui: quem está revisando, o que pediram e quando for publicado.

A palavra "Pull Request" não aparece para a pessoa (fica no "ver no GitHub" para quem quiser). O botão do topo ("Publicar") vira "Enviar para revisão" nesta fase.

Cada evento do GitHub vira uma linha aqui (e no chat): revisor entrou, comentou, pediu mudanças, aprovou. Os comentários aparecem na íntegra com o botão "Pedir para o Claude ajustar" — o Claude lê os apontamentos do PR, corrige na branch, envia e responde ao revisor. A pessoa não-técnica fecha um ciclo de code review sozinha.

O confete dispara UMA vez, no momento em que o Inhouse detecta o merge (mesmo que tenha sido a engenharia mergeando direto no GitHub) — com a tarefa aberta ou ao abrir depois (celebra na primeira visita). O card final guarda quem publicou e quando. Depois da festa, o widget de feedback de sempre.

7 O que acontece por baixo (resumo para aprovação)

Etapa nova "revisao" entre teste e publicar — só para projetos com GitHub (sem origin, o fluxo atual fica igual).
Acompanhamento: o Inhouse consulta o PR pelo gh (que já é dependência) a cada ~60s enquanto a tarefa está em Revisão: revisores, estado (comentou/pediu mudanças/aprovou), merge. Cada novidade vira linha no chat + evento ao vivo na UI. Sem webhooks, sem servidor exposto.
"Pedir para o Claude ajustar": o agente lê os comentários do PR, aplica as correções na branch da tarefa (mesma sessão, mesmo espaço), roda a verificação leve (preview vivo), faz push e comenta no PR ("ajustes aplicados") re-pedindo a revisão.
Publicar: habilita com a revisão aprovada (merge pelo Inhouse) — e se o time mergear direto, o Inhouse detecta e conclui com a mesma celebração.
PR fechado sem merge: a tarefa volta para "Seu teste" com a explicação do time — sem beco.
